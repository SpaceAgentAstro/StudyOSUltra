## 2024-05-22 - Unsafe AI Response Handling
**Vulnerability:** The `gradeOpenEndedAnswer` function directly called the AI service and parsed the result without error handling.
**Learning:** External AI services (LLMs) are unreliable. They can fail (network) or hallucinate (return invalid JSON).
**Prevention:** All AI service calls must be wrapped in `try-catch`. JSON parsing must be safe (e.g., using `zod` or `try-catch`). Always return a safe fallback object to the UI.
## 2026-04-29 - Securing Express APIs: Restricting CORS and Masking Internal Errors
**Vulnerability:** The Express backend had an overly permissive default CORS configuration (`app.use(cors())`) which allowed cross-origin requests from any domain in production. Additionally, the `/api/generate` and `/api/stream` endpoints leaked detailed stack traces and internal API error messages directly to the client (`res.status(500).json({ error: error.message || "Internal Server Error" })`).
**Learning:** Default configurations in utility libraries like `cors` often prioritize ease of development over security. Similarly, while detailed error messages are useful during local development, exposing them in a production API endpoint provides attackers with valuable intelligence about internal systems, third-party services (like Gemini SDK errors), and infrastructure.
**Prevention:** Always restrict CORS policies using environment-specific variables (e.g., `ALLOWED_ORIGINS`), explicitly permitting local development origins (`localhost`, `127.0.0.1`) while requiring explicit whitelisting for production domains. Ensure all API error handlers fail securely by logging detailed errors on the server side (`console.error`) but returning generic, sanitized error responses to the client (e.g., 'Internal Server Error').
